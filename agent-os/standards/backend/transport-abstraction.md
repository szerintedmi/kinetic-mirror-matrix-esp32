# Transport Abstraction

## Three Layers

1. **Command Execution** (platform-agnostic): `MotorCommandProcessor` → `CommandResult` with structured `Response`
2. **Response Schema** (unified): `ResponseLine` with type (kAck, kWarn, kError, kInfo, kData), msg_id, code, reason, fields
3. **Event Dispatcher** (async pub-sub): singleton `ResponseDispatcher` routes events to registered sinks

## Message Identity

- `msg_id`: internal UUID v4, generated by `transport::message_id::Next()` — used for async dispatcher routing
- `cmd_id`: client-provided or auto-generated UUID — used for MQTT request/response correlation
- Both exist simultaneously; `msg_id` binds stream to dispatcher events, `cmd_id` appears in MQTT payloads

## Event Routing (MQTT)

- Events emitted by dispatcher routed to "streams" (one per cmd_id)
- If stream not yet bound when event arrives, stored as "orphan" (max 16, LRU eviction)
- When stream binds to msg_id, orphan events replayed

## Response Normalization (Python CLI)

- Serial and MQTT responses normalize to same `ResponseEvent` dataclass
- Serial: parses `CTRL:ACK`, `CTRL:ERR`, `CTRL:WARN` prefixes
- MQTT: parses JSON with `status`, `action`, `cmd_id`, `result`, `warnings`, `errors`
- `source` field ("serial" or "mqtt") tracked but not rendered in logs
